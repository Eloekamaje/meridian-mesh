# Pilote retrieval sémantique — 2026-11-06

## Question

Le retrieval utilisait-il réellement des embeddings ? Sinon, que faut-il intégrer pour
passer à Bedrock, et cela explique-t-il les points faibles du benchmark conversationnel ?

## Constat avant correctifs

Le code **savait** faire du retrieval hybride :

- `embeddings.py` : Bedrock Titan/Cohere ou OpenAI ;
- `retrieval_hybride.py` : score `0,35 lexical + 0,45 sémantique + 0,15 graphe + 0,05 fraîcheur` ;
- `chunk_store.py` : stockage des vecteurs, modèle et dimension ;
- `bedrock_router.py` : profils `embedding` et `rerank`.

Mais dans l'environnement local :

- aucun `EMBEDDING_PROVIDER` ni clé OpenAI n'était configuré : le provider par défaut
  (`openai`) était indisponible et le retrieval retombait en **lexical + graphe** ;
- la table `document_chunk` de la base existante n'avait pas la colonne `embedding_dim` ;
- l'indexation passait un `dict` ACL à psycopg sans `Jsonb` : l'INSERT échouait ;
- ces erreurs étaient avalées par `except Exception: return 0` / `return []`, donc
  l'indexation documentaire échouait **silencieusement** ;
- `chunk_store` imbriquait `with conn:` dans `rls.contexte_tenant`, ce qui pouvait
  provoquer un conflit de transaction sur une connexion déjà en transaction.

Conclusion : le retrieval sémantique était **présent dans le code mais inactif et
silencieusement cassé** dans la base réelle. Les questions documentaires auraient été
servies en lexical seul, ou pas du tout.

## Correctifs

1. `backend/.env` : activation Bedrock Titan en `ca-central-1`, 1024 dimensions.
2. `scripts/migrer-document-chunk.py` : ajout idempotent de `embedding`,
   `embedding_model`, `embedding_dim`.
3. `chunk_store.py` :
   - `Jsonb(acl or {})` pour l'ACL ;
   - suppression des `with conn:` imbriqués dans `rls.contexte_tenant` ;
   - journalisation des échecs d'indexation/recherche/ACL ;
   - `reembedder()` pour les chunks sans vecteur ou d'un autre modèle.
4. `scripts/reembedder-documentation.py` : backfill des chunks existants.
5. `scripts/verifier-embeddings.py` : vérifie le provider, la dimension et la similarité
   de paraphrases.
6. `dependances.etat()` : `/api/health` expose désormais `embeddings`
   (`provider`, `modele`, `dimension`, `semantique`).
7. Benchmark `plugin/meridian/evals/retrieval/`.

### Benchmark retrieval

11 chunks, 12 requêtes paraphrasées :

| Métrique | Lexical + graphe | Hybride Bedrock |
|---|---:|---:|
| Hit@1 | 75 % | **100 %** |
| Hit@3 | 75 % | **100 %** |
| MRR | 0.797 | **1.000** |

Trois paraphrases passent de l'échec au premier rang grâce au sémantique :

- « corriger un texte déjà publié » → règles métier (9 → 1) ;
- « prouver son identité » → comptes/authentification (5 → 1) ;
- « bibliothèques Python » → dépendances (4 → 1).

## Ce que cela explique dans le benchmark conversationnel

### Expliqué par le retrieval

- Toute question **documentaire** (Confluence, SharePoint, pièces, RAG) était servie en
  lexical seul ou échouait silencieusement. C'est un vrai point faible, désormais
  corrigé et mesuré : **75 % → 100 % Hit@1** sur les paraphrases.
- Les réponses qui dépendent de documents paraphrasesé ou de vocabulaire métier
  différent pouvaient manquer le bon chunk.

### Non expliqué par le retrieval

Les points faibles restants du benchmark conversationnel ne sont pas des problèmes
d'embeddings :

- un run omet le nom exact de FastAPI alors que le claim et la preuve sont présents :
  c'est une fidélité de génération, pas un défaut de retrieval ;
- un run de prémisse fausse laisse une occurrence non niée de « est arrêtée » :
  c'est une discipline de langage, pas du retrieval ;
- un run de calibration utilise une formulation d'abstention que les marqueurs ne
  reconnaissent pas : c'est un problème de mesure, pas de retrieval ;
- le juge préfère parfois un refus concis du baseline : c'est un arbitrage de style.

## Limites

- Le corpus retrieval est synthétique et petit (11 chunks) ; il prouve la plomberie et
  la valeur des paraphrases, pas la qualité d'un RAG complet.
- Le reranker Bedrock n'est pas activé.
- Les embeddings sont des candidats, jamais des Claims : les preuves et les ACL restent
  l'autorité.
- Le backfill réel dépend des sources Confluence/SharePoint configurées ; le tenant
  `demo` n'a actuellement aucun chunk documentaire.
