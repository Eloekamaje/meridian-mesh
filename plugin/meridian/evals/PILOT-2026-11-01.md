# Pilote local — 2026-11-01

Périmètre : les deux workflows pilotes (`incident-paiements`, `changement-reglementaire`)
sur le runtime backend DeepSeek, avec un contrat structuré et un fixture séparé du tenant
`demo`.

**Claude Code n'a pas été utilisé.** Le runner [`run_deepseek.py`](run_deepseek.py) appelle :

- `POST /api/boucle/analyser` pour le contrat `socle`, `lecture`, `limites`, `actions`,
  `autorite`, `prochaines_etapes`, `decision_support` ;
- `POST /api/aurora/demander` pour la prose DeepSeek et son usage (latence, jetons, coût).

Le backend tourne avec `JUMEAU_MODELE=deepseek` et `DEEPSEEK_API_KEY` (clé jamais affichée).

## Fixture synthétique `pilot`

Le tenant `demo` n'est pas modifié. Le seed crée un tenant séparé `pilot`, clairement marqué
`[SYNTHÉTIQUE]`, avec :

- 4 Twins : `paiements`, `comptes`, `fraude`, `support` ;
- 2 Situations canoniques : `sit-latence-paiements`, `sit-anomalie-fraude` ;
- 6 Claims/Preuves minimales portant les termes des scénarios (`SLA`, `preuve`, `R-118`,
  `limite`, `impact`, `interface`, `approbation`).

L'API n'expose pas de route de création de Situation : le seed écrit via les dépôts
canoniques (`twins_types`, `entreprise_depot`) et refuse tout autre tenant que `pilot`.

```bash
cd backend
PYTHONPATH=..:../backend .venv/bin/python ../plugin/meridian/evals/seed_pilot.py
```

Résultat :

- Twins créés : `paiements`, `comptes`, `fraude`, `support` (tenant `pilot`) ;
- Situations : `sit-latence-paiements` et `sit-anomalie-fraude`, version `1` ;
- Claims : 6, tous `PROPOSED`, avec 6 preuves SUPPORT synthétiques ;
- Deuxième exécution : mêmes identifiants, mêmes versions, aucun doublon ; `demo` conserve
  ses 1 187 claims et ses 3 Twins.

## Critères

Claude. Les échos de la question sont retirés du texte du contrat avant notation. Le contrat
expose `limites` dans `socle.limites` : le contrôle de structure le reconnaît à ce niveau,
sans relâcher les termes ni les sections attendus.

## Limites

- Le fixture `pilot` est **synthétique** : il prouve le contrat et le chemin de données, pas
  un état de production.
- Les prompts des scénarios conservent la mention historique `tenant demo` ; le tenant
  effectif est porté par `X-Tenant: pilot`. Le contrat structuré et les Claims lus sont bien
  ceux de `pilot`.
- La surface `situation` de `/boucle/analyser` n'accepte que `situation_id` : le runner envoie
  la situation, pas la liste des Twins. Les Twins sont vérifiés séparément via
  `/boucle/twins` et les Claims du tenant portent le contexte.
- `impact` et `approbation` sont satisfaits par le texte du contrat (preuves synthétiques) et
  la prose, pas par une section top-level `impact` : le spécialiste d'impact n'a pas de
  graphe Neo4j pour `pilot`.
- Un run par scénario : aucune moyenne, aucun test statistique.
- Aucune revue humaine, aucun outcome réel ; ce pilote ne démontre pas la production readiness.
- Le coût est une estimation du backend (`usage.cout`), pas une facture.
